Abstract

This study asks which existing pages an editor should review first when refresh capacity is limited. It uses the bundled FlyRank anonymized starter release: 30,000 content items from 32 pseudonymous clients, with trailing-90-day search and engagement measurements. I compare a transparent rule score with Logistic Regression, a constrained Decision Tree, and a Random Forest, keeping label-derived fields and identifiers out of the features and holding out entire clients for evaluation. On the reference client holdout, Random Forest raised precision among the first 50 recommendations from 0.24 for the rule baseline to 0.74, while average precision rose from 0.468 to 0.618. The result supports a human-reviewed refresh queue; it does not show that refreshing a recommended page will cause traffic to improve.

01

Introduction / Problem statement

An editor may manage thousands of pages but have time to refresh only a small batch each week. The useful decision is not “is this page good?” but “which page should be inspected first?”

The unit of analysis is one pseudonymized content item. The output is a ranked score with a suggested action and reason codes. A human editor checks each recommended page in context and decides whether to refresh, expand, investigate click-through rate, investigate engagement, or monitor.

A false positive costs review time. A false negative can leave a declining, still-visible page unattended. Machine learning is useful only if it improves that ordering over a clear, hand-written rule.

02

Data

The analysis uses the bundled FlyRank starter release, data/raw/content_refresh_anonymized.csv. It contains 30,000 rows and 44 columns at one row per pseudonymized content item across 32 clients. Metrics summarize a trailing 90-day snapshot; exact calendar dates are not exposed, so this paper does not invent them or make time-forward claims.

Public-safety boundary

No client names, URLs, domains, titles, keywords, or raw queries appear in the analysis. Pseudonymous IDs are used only for grouping and joins.

Rate columns are percentages multiplied by 100, so ctr = 0.76 means 0.76%. An average position of zero means no position data. The label sources trend_direction and trend_pct, overlapping recent-window fields, provider/model metadata, and identifiers are excluded from features.

03

Methodology

Target and baseline

The proxy target is is_declining_label = (trend_direction == "down"). It describes observed decline inside the snapshot, not a future outcome. The baseline prioritizes stale but visible pages, visible pages with low CTR, thin but visible pages, and old pages that still rank on page one.

Models and features

The reference pipeline compares Logistic Regression, a constrained Decision Tree, and a constrained Random Forest. Features cover demand, content shape, traffic volume, days with activity, age and freshness, click-through rate, average position, engagement, scroll rate, and public categorical tiers. Missing values are handled during preprocessing.

Validation and leakage checks

Complete clients are held out, producing 27,675 training rows and 2,325 test rows with seed 42. Models and the baseline are evaluated on the same held-out pages. Assertions prevent label sources, overlapping windows, and identifiers from entering the feature matrix. Model selection uses precision@50 first, then average precision and ROC AUC.

Sensitivity check

A separate grouped holdout selected Logistic Regression at precision@50 = 0.72 versus a 0.38 rule baseline; Random Forest reached 0.54. The learned ranking improved on the rule again, but the winning algorithm changed. The honest conclusion is improvement on the tested client splits, not a universally best algorithm.

05

Limitations & honest framing

  • Not a forecast. The target is an in-window decline proxy, not a future label.
  • Not time validation. Client holdout tests transfer across clients, not through time.
  • Split-sensitive. Only 32 clients are available, and the selected model changes across grouped holdouts.
  • Not causal. Feature importance does not identify causes, and no randomized experiment estimates refresh impact.
  • Human review required. A high score is a reason to inspect a page, not permission to edit it automatically.

06

Ranked recommendations

The repeatable pipeline scores all 30,000 items after validation and combines model probability with the transparent baseline. The editor should work through the queue in this order:

  1. 01
    Review high-confidence visible candidates

    Start where model probability, real impressions, and multiple reason codes agree.

  2. 02
    Refresh and review CTR

    Check current intent, title and snippet alignment, and live ranking context.

  3. 03
    Review engagement

    Inspect intent satisfaction and tracking when sessions are meaningful but engagement is weak.

  4. 04
    Expand only after confirmation

    Add coverage only when a human verifies a genuine content gap.

  5. 05
    Monitor low-confidence items

    Defer unless new evidence or business priority changes the decision.

No-go actions

Never automate publication, deletion, redirects, client communication, or promises of traffic recovery from this score.
